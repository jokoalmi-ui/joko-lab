## Hallazgos

### Archivos analizados

| Archivo | Ruta | Tipo | Contenido |
|---|---|---|---|
| state.json | /mnt/ssd_ia_datos/lab-state/state.json | Producido (cada 60s) | Estado real del lab: GPU, RAM, servicios, cloud, políticas |
| state.schema.json | /mnt/ssd_ia_datos/lab-state/state.schema.json | Schema | Define contrato de state.json (campos obligatorios, tipos) |
| ultima-decision.json | ~/.hermes/ultima-decision.json | Caché (sobrescrito) | Última decisión del DE: provider, model, reason |
| config.yaml | ~/.hermes/config.yaml | Configuración Hermes | Config completa de Hermes (model, delegación, etc.) |
| ultima-decision.json | /mnt/ssd_ia_datos/lab-state/... | No existe | No hay copia en lab-state |
| decision.log | /mnt/ssd_ia_datos/lab-state/logs/decision.log | Log histórico | Cada decisión del DE (append) |
| apply-decision.log | /mnt/ssd_ia_datos/lab-state/logs/apply-decision.log | Log histórico | Cada ejecución de apply-decision.sh (append) |

### ¿Qué archivo es la verdad?

**state.json** es la fuente principal de verdad del laboratorio. Es el único archivo
que contiene datos observados del sistema real (GPU, RAM, servicios activos,
disponibilidad de cloud). Lo produce state-manager.py cada 60 segundos.

### ¿Qué archivos son caché?

| Archivo | Por qué es caché |
|---|---|
| ultima-decision.json (~/.hermes/) | Contiene la última decisión. Se sobrescribe en cada resolve(). Es un snapshot, no un registro histórico. |
| decision.log | Registro histórico (append). No es fuente de verdad de estado actual, es auditoría. |

### ¿Qué archivos son derivados?

| Archivo | Derivado de |
|---|---|
| ultima-decision.json | Salida del decision_engine.py al finalizar resolve() |
| apply-decision.log | Ejecución de apply-decision.sh |
| decision.log | decision_engine.py (append en cada resolve()) |
| config.yaml (model.provider, model.default) | apply-decision.sh → hermes config set |
| state.json | state-manager.py (observación directa del hardware y servicios) |

### ¿Qué archivos pueden eliminarse?

| Archivo | Propuesta | Motivo |
|---|---|---|
| gpu.yaml | Puede eliminarse | No lo consume nadie. El DE no lo lee. La info de GPU ya está en state.json. |
| niveles.yaml | Puede eliminarse | No lo consume nadie. El DE no lo lee. No hay sistema de verificación implementado. |

### Duplicidades detectadas

1. **ultima-decision.json escrito por dos componentes:**
   - decision_engine.py línea 376: `save_ultima_decision(result)`
   - apply-decision.sh línea 60: `echo "$DECISION" > ~/.hermes/ultima-decision.json`
   - Son dos escritores distintos al mismo archivo. Si el cron ejecuta apply-decision.sh
     mientras el DE está haciendo resolve(), hay riesgo de corrupción.

2. **Disponibilidad duplicada:** La política de disponibilidad está codificada inline
   en decision_engine.py (función evaluar_disponibilidad) pero no tiene archivo YAML
   propio. El contrato dice que las políticas deben ser declarativas.

3. **Preferencias duplicadas:** Igual que disponibilidad. FALLBACK_PROVIDER y
   FALLBACK_MODEL son constantes en el código Python. Deberían estar en un YAML.

4. **modelos.yaml tiene un modelo incorrecto:** El default de deepseek es
   "deepseek-chat" (línea 18 de modelos.yaml) pero Hermes usa "deepseek-v4-flash"
   como FALLBACK_MODEL. Hay inconsistencia.

5. **state.json tiene hora distinta a la real:** state.json se generó a las 12:06
   pero ultima-decision.json dice "ahora 11:59". La decisión estaba basada en un
   state.json anterior. Esto es normal por el polling de 60s, pero indica que
   la decisión puede usar datos de hasta 60s de antigüedad.

### Relación state.json → config.yaml

```
state.json                          config.yaml
──────────                          ──────────
cloud.deepseek.disponible            model.provider → deepseek
cloud.gemini.disponible              
services.ollama.activo               
policies.hora.actual                 
policies.hora.franja_activa          
                                     delegation.provider → openai (Ollama)
                                     delegation.base_url → http://localhost:11434/v1
                                     delegation.model → qwen2.5:7b
```

- **state.json** decide el proveedor principal de Hermes (model.provider)
- **config.yaml** tiene la delegación local configurada aparte, no la toca el DE
- **config.yaml** NO es fuente de verdad del estado del laboratorio. Es configuración de Hermes.
- **state.json** NO es configuración de Hermes. Es el estado observado.

## Riesgos

1. **Dos escritores de ultima-decision.json.** apply-decision.sh y decision_engine.py
   escriben al mismo archivo. Si coinciden, el archivo puede quedar corrupto.

2. **Disponibilidad y Preferencias no son declarativas.** Están en código Python,
   no en YAML. Violan el principio de "políticas declarativas" del contrato.
   También están ausentes del orden de precedencia visible en policies/.

3. **modelos.yaml default incorrecto para deepseek.** Dice "deepseek-chat" pero
   Hermes usa "deepseek-v4-flash". El DE usa FALLBACK_MODEL="deepseek-v4-flash",
   ignorando el YAML para el fallback.

4. **state.json puede estar desfasado hasta 60s.** La decisión del DE se basa en
   datos que pueden tener hasta un minuto de antigüedad. Para cambios de franja
   horaria no es crítico, pero para disponibilidad sí.

5. **config.yaml contiene el provider activo que aplicó apply-decision.sh, pero**
   no hay verificación de que ese provider coincida con la última decisión del DE.

## Recomendación

Resolver las duplicidades de escritura de ultima-decision.json: un solo escritor.
Extraer disponibilidad y preferencias a YAML para que todas las políticas sean
declarativas. Corregir modelos.yaml para que deepseek default coincida con el
modelo real que usa Hermes.

FASE 3 — Flujo Runtime real
═══════════════════════════════════════════════════════════════

## Hallazgos

### Flujo ideal (según CONTRACT.md)

```
Usuario
   ↓
Hermes
   ↓
Runtime.resolve(task_hint) → API Python
   ↓
Decision Engine → lee state.json + policies/*.yaml
   ↓
Decide: {provider, model, reason}
   ↓
apply-decision.sh → hermes config set
   ↓
Hermes usa el nuevo provider
   ↓
Respuesta al usuario
```

### Flujo real (código)

```
State Manager (cada 60s o bajo demanda)
   ↓
Escribe state.json
   ↓
Cron (0 3, 0 12, */30)
   ↓
apply-decision.sh
   ↓
Llama a decision_engine.py --json (subproceso)
   ↓
DE: load_state() → state.json
    → load_yaml() → policies/*.yaml
    → evalúa 5 políticas en orden
    → save_ultima_decision() → ~/.hermes/ultima-decision.json
    → log_decision() → decision.log
    → devuelve dict {provider, model, reason}
   ↓
apply-decision.sh parsea JSON con Python inline
    → hermes config set model.provider
    → hermes config set model.default
    → escribe ~/.hermes/ultima-decision.json (DE duplica)
    → escribe apply-decision.log
   ↓
Hermes (siguiente sesión) usa el provider/config actual
```

### Ruta que NO existe (según CONTRACT.md pero sin implementar)

- Runtime.resolve() — NO implementado. No hay runtime/api.py.
- El CONTRACT.md describe Runtime.resolve(task_hint) pero el DE se llama directamente.

### Acoplamientos detectados

| Acoplamiento | Descripción | Impacto |
|---|---|---|
| apply-decision.sh → config.yaml | Lee y escribe config.yaml con hermes config | Si el formato de config.yaml cambia, apply-decision.sh se rompe |
| DE → ultima-decision.json (2 escritores) | DE escribe save_ultima_decision() y apply-decision.sh también | Riesgo de corrupción |
| DE → state.json (ruta absoluta) | STATE_FILE = /mnt/ssd_ia_datos/lab-state/state.json | Si la ruta cambia, el DE se rompe |
| state-manager → Docker compose exec | Usa docker compose exec ollama para versión | Dependencia de Docker en componente que debería ser ligero |
| apply-decision.sh → hermes CLI | Depende de hermes config set/show | Si Hermes CLI cambia su API, el script se rompe |

### Dependencias ocultas

| Dependencia | Dónde aparece | Problema |
|---|---|---|
| SECRETS_DIR | state-manager.py línea 191 | Define /mnt/ssd_ia_datos/lab-state/secrets y lee gemini.key. Si no existe la clave, el error se traga silenciosamente. |
| yaml (PyYAML) | decision_engine.py líneas 21-24 | try: import yaml. Si no está instalado, usa parser manual _parse_yaml_simple. Dos caminos de parseo → posible inconsistencia. |
| nvidia-smi | state-manager.py | Si no está instalado, GPU devuelve "no detectada" pero sigue funcionando. |
| curl | state-manager.py (7 llamadas) | Dependencia externa para healthchecks. Sin curl, todos los servicios aparecen como inactivos. |

### SPOF detectados

| SPOF | Componente | Si falla... |
|---|---|---|
| state.json | DE | DE no puede decidir → cae a fallback (ultima-decision.json o defaults) |
| state-manager.py | No hay watchdog | Si se para, state.json se congela. Nadie lo reinicia automáticamente. |
| apply-decision.sh | DE → Hermes | Si falla el cron no actualiza config.yaml. Hermes se queda con el último provider. |
| cron (usuario) | Todas las automatizaciones | Si el crontab se corrompe, el Runtime deja de actualizarse. |
| ~/.hermes/config.yaml | Hermes | Si se corrompe, Hermes no arranca. apply-decision.sh falla. |

### Duplicidades en el flujo

| Duplicidad | Componentes | Detalle |
|---|---|---|
| ultima-decision.json | DE + apply-decision.sh | Ambos escriben el mismo archivo |
| Log de decisión | DE (decision.log) + apply-decision.sh (apply-decision.log) | Información parcialmente duplicada |
| Parseo de JSON | apply-decision.sh líneas 28-30 | Tres llamadas python3 -c para parsear un mismo JSON |

## Riesgos

1. El flujo real NO pasa por Runtime.resolve(). No hay API. El contrato describe una interfaz que no existe.
2. state-manager.py es el único componente que escribe state.json. Sin watchdog, si se para el proceso el estado se congela.
3. apply-decision.sh parsea JSON tres veces (provider, model, reason) cuando podría hacerlo en una sola llamada.
4. La decisión del DE no se verifica contra la realidad. apply-decision.sh ejecuta hermes config set y da por hecho que funcionó.
5. Si el cron se ejecuta 50 veces al día y apply-decision.sh tarda ~7.5ms, el coste es irrelevante. Pero el riesgo de que dos ejecuciones coincidan (ultima-decision.json) es real.

## Recomendación

Implementar Runtime.resolve() como API para que el contrato y la implementación coincidan. Eliminar el doble escritor de ultima-decision.json. Añadir watchdog para state-manager.py.

## Hallazgos

### ¿Existe runtime/api.py?

**No.** No existe ningún archivo api.py en runtime/. El directorio solo tiene CONTRACT.md y VERSION.

### Compatibilidad CONTRACT.md vs implementación

| Aspecto del contrato | CONTRACT.md dice | Implementación real (decision_engine.py) | Compatible |
|---|---|---|---|

| Salida: model | string, obligatorio | result["model"] | Sí |
| Salida: reason | string, obligatorio | result["reason"] | Sí |
| Salida: policy | string, obligatorio | NO incluido | ❌ |
| Salida: privacy | "cloud" o "local", obligatorio | NO incluido | ❌ |
| Salida: verification | "LOW"/"MEDIUM"/"HIGH", obligatorio | NO incluido | ❌ |
| Salida: confidence | float 0.0-1.0, obligatorio | NO incluido | ❌ |
| Salida: expires | ISO 8601, obligatorio | NO incluido | ❌ |
| Salida: decision_id | string, obligatorio | NO incluido | ❌ |

| Registro: ultima-decision.json | DE escribe (responsabilidad del Runtime) | Sí, save_ultima_decision() | Sí |
| Registro: decision.log | DE escribe (append) | Sí, log_decision() | Sí |

### Faltan 6 campos obligatorios en la salida real

La salida actual del DE:
```
{"provider": "gemini", "model": "gemini-2.5-pro", "reason": "Horario: ..."}
```

La salida que exige el contrato (sección 3):
```
{"provider": "gemini", "model": "gemini-2.5-pro", "reason": "Horario: ...",
 "policy": "horario.yaml", "privacy": "cloud", "verification": "LOW",
 "confidence": 1.0, "expires": "2026-07-14T12:00:00+02:00",
 "decision_id": "20260714-103812-a1f4"}
```

Campos faltantes:
1. policy — nombre del archivo de política que ganó
2. privacy — "cloud" o "local"
3. verification — nivel de verificación
4. confidence — 0.0 a 1.0
5. expires — ISO 8601 de caducidad
6. decision_id — identificador único

### ¿Quién debería consumir Runtime?

Según el contrato, apply-decision.sh debe llamar a Runtime.resolve() vía
python3 runtime/api.py --json. Pero runtime/api.py NO existe.
En su lugar, apply-decision.sh llama directamente a decision_engine.py --json.

### Lógica duplicada

| Concepto | Dónde aparece | Problema |
|---|---|---|
| Definición de la API | CONTRACT.md sección 3 | Define Runtime.resolve() pero no existe |
| Implementación real | decision_engine.py decide() | Firma parecida pero nombre y salida incompatible |
| Parseo de la decisión | apply-decision.sh (3 llamadas python3) | Podría ser una sola llamada |
| Escritura de ultima-decision.json | DE + apply-decision.sh | Dos escritores |

## Riesgos

1. El contrato y la implementación NO son compatibles. La salida del DE tiene 6 campos menos de los obligatorios.
2. Cualquier código que consuma Runtime.resolve() esperando el formato del contrato recibirá un dict incompleto.
3. apply-decision.sh llama al DE directamente, no a través de la API definida en el contrato. Si se implementa runtime/api.py en el futuro, apply-decision.sh no lo usará.
4. No hay versión de la implementación. CONTRACT.md tiene v1.0 (en VERSION) pero el DE no tiene versión propia.

## Recomendación

Sincronizar la salida del DE con el contrato: añadir los 6 campos faltantes. Crear runtime/api.py como wrapper del DE para que el contrato y la implementación coincidan. apply-decision.sh debería consumir Runtime.resolve() en lugar del DE directamente.

FASE 5 — Decision Engine (solo decide)
═══════════════════════════════════════════════════════════════

## Hallazgos

### ¿Solo decide?

La función decide() (líneas 308-377) es mayoritariamente pura:
recibe task_hint, lee state.json, evalúa políticas, devuelve {provider, model, reason}.
Hasta ahí, correcto.

### Violaciones detectadas

**Violación 1: Escribe en ~/.hermes/ (directorio de configuración de Hermes)**

Línea 376: save_ultima_decision(result)

save_ultima_decision() (líneas 131-136) escribe en ~/.hermes/ultima-decision.json.
El DE está escribiendo en el directorio de configuración de Hermes.

El contrato (sección 9) dice que el DE DEBE escribir ultima-decision.json.
Pero el principio "solo decide" dice que NO DEBE escribir configuración.
Hay conflicto entre el contrato y la pureza del DE.

**Violación 2: Lee de ~/.hermes/ como fallback**

Línea 30: ULTIMA_DECISION = Path.home() / ".hermes" / "ultima-decision.json"

El DE lee ultima-decision.json de ~/.hermes/ si state.json no existe.
Funcionalmente correcto, pero mete al DE dentro del espacio de Hermes.

**Violación 3: Escribe decision.log**

Línea 375: log_decision(...)

El contrato dice que el DE debe escribir el log. Pero añade responsabilidad
de escritura a un componente que idealmente solo decide.

### Tabla de verificación

| Principio | ¿Cumple? | Evidencia |
|---|---|---|
| Solo decide | ❌ Parcialmente | Decide (decide()) + escribe (save_ultima_decision, log_decision) |
| No escribe configuración | ❌ | Escribe en ~/.hermes/ultima-decision.json |
| No modifica políticas | ✅ | Solo lee policies/*.yaml, nunca escribe |
| No conoce secretos | ✅ | No lee secrets. API keys no están en su código. |
| No lee config.yaml | ✅ | No referencia ~/.hermes/config.yaml |
| No ejecuta herramientas | ✅ | No llama a curl, nvidia-smi ni Docker |
| Es determinista | ✅ | Misma entrada → misma salida (sin LLM, sin aleatoriedad) |
| Sin LLM | ✅ | Cien por cien Python puro |

### ¿Quién debería decidir vs quién escribe?

Estado actual:
```
decide() ──→ devuelve dict
          ──→ save_ultima_decision()  ← escribe en ~/.hermes/
          ──→ log_decision()         ← escribe en lab-state/logs/
```

Estado ideal:
```
decide() ──→ devuelve dict ← solo decide
             ↓
        runtime/api.py  ← escribe ultima-decision.json + decision.log
```

### Conflicto con el contrato

El contrato (sección 9.2) dice:
"El Runtime es responsable de registrar cada decisión que toma."

Si el DE es el Runtime, entonces debe escribir los logs (según contrato).
Si el DE debe "solo decidir" (según Fase 5), entonces no debería escribir nada.

Hay una contradicción entre el principio de la Fase 5 y el contrato vigente.

### Punto clave

El DE es un motor de decisión puro en su núcleo (decide()), pero tiene efectos
secundarios (escritura de archivos). Para que "solo decida", esos efectos
secundarios deben moverse a la capa de aplicación (runtime/api.py o
apply-decision.sh).

## Riesgos

1. El DE escribe ultima-decision.json en ~/.hermes/. Si Hermes cambia la
   estructura de su directorio, el DE se rompe.
2. apply-decision.sh también escribe ultima-decision.json. Conflicto de escritores.
3. El contrato obliga al DE a escribir logs. Si se quiere un DE puro (solo decide),
   hay que modificar el contrato.

## Recomendación

Separar responsabilidades: el DE devuelve la decisión y runtime/api.py (o
apply-decision.sh) se encarga de escribir logs y archivos de estado.
El contrato debería actualizarse para reflejar que el DE solo decide.

FASE 6 — State Manager
═══════════════════════════════════════════════════════════════

## Hallazgos

### Frecuencia

| Modo | Frecuencia | Cómo se invoca |
|---|---|---|
| run_once() | Bajo demanda | python3 state-manager.py |
| run_watch() | Cada 60 segundos | python3 state-manager.py --watch |

El modo watch es un bucle while True. No hay watchdog del sistema (systemd) que

- Peor caso (todo caído esperando timeouts): ~46s por ciclo
- Caso normal (todo responde): ~8-10s por ciclo

### SECRETS_DIR (línea 191)

```
SECRETS_DIR = Path("/mnt/ssd_ia_datos/lab-state/secrets")
```

Se usa para leer gemini.key (línea 256) y pasarlo a check_cloud(). Si la clave
no existe o el archivo está vacío, check_cloud() recibe api_key="" y la llamada
curl a Gemini se hace sin key. Gemini devuelve 403, y check_cloud() interpreta
"disponible: true" porque 401/403/429 se consideran "API existe".

Esto significa que Gemini aparece como disponible incluso si la API key es
inválida o no existe.

## Riesgos

1. Sin watchdog: si state-manager.py se para, state.json se congela. El DE
   sigue decidiendo con datos obsoletos hasta que ultima-decision.json caduque.
2. Timeout global inexistente: si una llamada (ej: DeepSeek API) se queda
   bloqueada más del timeout individual, el ciclo entero se retrasa.
3. 7 de 15 llamadas son polling innecesario cada 60s — consumo de recursos
   y logs que podrían reducirse.
4. Gemini aparece como disponible aunque la API key sea inválida (código
   401/403 interpretado como disponible).
5. docker compose logs --tail=30 n8n es pesado para obtener solo un campo.
   En un ciclo de 60s, traer 30 líneas de log cada vez es innecesario.

## Recomendación

Separar polling en dos frecuencias: cada 60s lo crítico (GPU, n8n healthz,
cloud disponibilidad) y cada 5-10 min lo estable (versiones, modelos instalados).
Añadir watchdog systemd o timer para state-manager. Corregir la interpretación
de 401/403 en check_cloud() para que no se confundan con "disponible".

**Conflicto 1: Disponibilidad puede saltarse Horario (normal, por precedencia)**

**Conflicto 2: Política de costes INOPERANTE**

costes.yaml define saldo_minimo_usd: 5.00. Pero state.json devuelve
saldo_usd: null para DeepSeek y Gemini porque check_cloud() nunca rellena ese
campo. evaluar_costes() comprueba "if ds_saldo is not None" — al ser null,

**Conflicto 3: Fallback de horario.yaml dice ollama, pero el código tiene deepseek**

horario.yaml:
```
fallback:
  proveedor: ollama
```

Código:
```
proveedor_fb = fb.get("proveedor", FALLBACK_PROVIDER)  # deepseek
```

El YAML actual tiene proveedor: ollama, así que el código usa ollama. Pero si
alguien edita el YAML y quita "proveedor", el código cambia silenciosamente a
DeepSeek. Es frágil.

**Conflicto 4: modelos.yaml default para deepseek es "deepseek-chat" pero
Hermes usa "deepseek-v4-flash"**

modelos.yaml línea 18:
```
deepseek:
  default: deepseek-chat
```

Código línea 35:
```
FALLBACK_MODEL = "deepseek-v4-flash"
```

Dependiendo del camino de decisión, el modelo puede ser "deepseek-chat" (vía
_modelo_por_proveedor) o "deepseek-v4-flash" (vía FALLBACK_MODEL).

**Conflicto 5: Notación horaria confusa**

horario.yaml:
```
- horas: "12:00-03:00"
  proveedor: deepseek
```

"12:00-03:00" cruza la medianoche. El código lo maneja correctamente, pero
un humano puede malinterpretarlo como rango inverso.

## Hallazgos

Basada en los hallazgos de las 11 fases anteriores y la revisión del usuario.

**4 causas raíz que eliminan >80% de la deuda técnica actual.**

### 🔴 Prioridad 1 — El contrato no se cumple

Problema: existe runtime/CONTRACT.md pero el código no pasa por Runtime.resolve().
El DE se llama directamente. La API del contrato es bypassada.

Es el equivalente a diseñar una API REST y que todos los programas accedan
directamente a la base de datos.

Solución:
```
Usuario
    │
    ▼
Runtime.resolve()
    │
    ▼
Decision Engine
```

Todo debe pasar por Runtime.resolve(). Hasta que exista, el contrato es
solo documentación.

### 🔴 Prioridad 2 — El DE hace demasiado

El DE decide bien pero:
- Escribe en ~/.hermes/ultima-decision.json
- Escribe decision.log
- Tiene dependencias del directorio de Hermes (~/.hermes/)

Solución: el DE debe ser solo:
```
input → decisión → JSON
```
Nada más. Ni logs. Ni config. Ni escribir archivos. Ni modificar Hermes.

### 🔴 Prioridad 3 — No existen tests

0 tests en el componente más importante del laboratorio.
Cualquier cambio puede romper precedencia, privacidad, fallback, horarios
o modelos sin que nadie lo note.

Solución: tests mínimos antes de seguir desarrollando.

### 🔴 Prioridad 4 — Las políticas no son la verdad completa

2 políticas inline en código Python (disponibilidad, preferencias).
2 políticas huérfanas (gpu, niveles).

Parte de las reglas vive en policies/*.yaml y otra parte en decision_engine.py.

Solución: 100% de las reglas en YAML. Python solo interpreta.

### 🟠 Después de las 4 prioridades

- Reducir llamadas del state-manager (15/ciclo → menos)
- Añadir watchdog systemd
- Tests de contrato (Runtime.resolve() → ¿cumple CONTRACT.md?)
- Observabilidad estructurada: decision-ledger.json DESCARTADO (2026-07-15). decision.log cubre la necesidad.

### 🟡 Documentación al final

Las contradicciones en docs son normales tras refactorizaciones. Se corrigen
al final, cuando el código esté estable.
