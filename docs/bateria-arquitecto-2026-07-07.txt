NIVEL 1 — COMPRENSIÓN DEL LABORATORIO
================================================================================

1 — Objetivo principal de Joko Lab

Según HERMES.md §1:
"Joko Lab es un laboratorio personal para diseñar, documentar y evolucionar un
entorno de automatización e inteligencia artificial de forma incremental,
reproducible y mantenible. Su objetivo es facilitar el aprendizaje, la
experimentación y la construcción de soluciones útiles sobre una infraestructura
propia."

Además, la filosofía operativa (§2b) añade que toda mejora debe cumplir al menos
uno de:
- Reducir trabajo futuro
- Aumentar el conocimiento del sistema
- Mejorar la capacidad de operar autónomamente

No hay otro objetivo documentado en ningún sitio.


2 — Papel de HERMES.md

HERMES.md es la constitución del laboratorio. Según estado-real.md:
"Define principios, normas y organización. Ninguna skill lo modifica."

Según joko-lab/SKILL.md: "La identidad, principios y normas del laboratorio
están definidos en HERMES.md, que es la fuente de verdad."

Contiene:
- Filosofía del laboratorio (5 principios + filosofía operativa)
- Organización de skills (etapas y niveles de madurez)
- Estilo de comunicación
- Principios de seguridad
- Flujo de trabajo
- Mejora continua
- Registro de decisiones

No es una skill. No pertenece a ningún nivel jerárquico. Todas las skills lo
referencian.


3 — Diferencia entre HERMES.md y joko-lab

HERMES.md:
- Naturaleza: Documento constitución
- Nivel jerárquico: Ninguno (techo)
- Contiene: Principios, normas, organización
- Modificable por: Solo por decisión explícita
- Quién lo consulta: Todas las skills

joko-lab:
- Naturaleza: Skill
- Nivel jerárquico: Nivel 1 — Identidad
- Contiene: Contexto global (infraestructura, hardware, stack Docker,
  proveedores IA)
- Modificable por: Sí, actualizable
- Quién lo consulta: Skills que necesitan contexto del entorno

joko-lab aporta el "dónde estamos" (infraestructura, hardware, stack Docker).
HERMES.md define "cómo trabajamos" (principios, normas, flujo). No se solapan
desde la poda realizada.


4 — Responsabilidad de lab-manager

Según lab-manager/COMMANDS.md:
"lab-manager responde preguntas de gestión y diagnóstico. No ejecuta acciones
técnicas ni modifica archivos. Su trabajo es pensar, coordinar e interpretar."

Según estado-real.md:
"Audita, detecta incoherencias, prioriza trabajo, revisa documentación.
Consulta a especialistas pero no ejecuta."

Tiene 4 scripts de diagnóstico que ejecuta para obtener datos, pero no toca
servicios, archivos de configuración ni modifica el sistema. Es el Arquitecto
Técnico del laboratorio. No administra nada directamente. Administra el
laboratorio como concepto.


5 — Qué skill consultar para Docker y Hermes

Pregunta: "¿Los contenedores están UP?" -> Skill: docker-admin
Pregunta: "¿Cómo reinicio un servicio?" -> Skill: docker-admin
Pregunta: "¿Hermes está bien configurado?" -> Skill: hermes-expert
Pregunta: "¿Cambio el provider de Hermes?" -> Skill: hermes-expert

Está documentado en estado-real.md (tabla de roles) y en lab-manager/COMMANDS.md:
"Cuando necesite información de un sistema concreto (Docker, n8n, Hermes),
consulta a la skill especializada (docker-admin, n8n-admin, hermes-expert)."


6 — Fuentes de verdad vs documentos de referencia

HERMES.md — ES fuente de verdad. Otros que lo referencian: joko-lab (lo cita),
todas las skills.

joko-lab/SKILL.md — NO es fuente de verdad. Ninguna lo referencia.

docker-admin/* — ES fuente de verdad para Docker. lab-manager lo consulta.

n8n-admin/* — ES fuente de verdad para n8n. lab-manager lo consulta.

estado-real.md — NO es fuente de verdad. Es un snapshot, no autoridad normativa.

docs/decisiones/ — ES fuente de verdad. lab-manager los enumera.

estado-real.md es especialmente delicado: contiene información que caduca
(versiones, niveles de madurez, scripts). Debería marcarse explícitamente como
snapshot, no como fuente de verdad.

  Todas las skills (se ejecutan dentro de sesiones de Hermes)

Si Hermes dejara de funcionar, el laboratorio como concepto documental sobrevive
(los archivos están en disco), pero la capacidad de operar y consultar skills
desaparece. Es una dependencia existencial del laboratorio como sistema vivo.


10 — Si Docker dejara de funcionar

Afectados:
  n8n — Se para. Workflows inaccesibles.
  Ollama — Se para. Modelos locales no disponibles.
  Stirling-PDF — Se para.
  pdf-cleaner — Se para.
  docker-admin — Pierde su objeto de gestión.
  n8n-admin — Pierde su objeto de gestión.

No afectados:

  evolution — Corre fuera de Docker.
  hermes-expert — Hermes Agent corre fuera de Docker.
  LM Studio — Corre fuera de Docker.
  perfumes — No depende de Docker.

El laboratorio no colapsa, pero pierde su capa de automatización y modelos
locales por Ollama.


11 — Si DeepSeek dejara de estar disponible

Según joko-lab/SKILL.md, DeepSeek es el proveedor principal de Hermes.

Afectados:
  Hermes Agent — Pierde su provider principal. Habría que reconfigurarlo.
  lab-manager — No podría responder sin modelo activo.
  Todas las skills — Dependen de que Hermes funcione.

Mitigación posible: cambiar Hermes a Ollama o LM Studio como provider.
DeepSeek no es imprescindible — el laboratorio puede funcionar 100% local
con Ollama + LM Studio.


12 — Partes que funcionan completamente en local

Proveedores de IA local (según joko-lab/SKILL.md):
  Ollama (localhost:11434) — Funciona sin internet: SÍ
  LM Studio (localhost:1234) — Funciona sin internet: SÍ
  DeepSeek (API online) — Funciona sin internet: NO

Con DeepSeek caído pero Ollama + LM Studio activos, funcionan 100% local:
  n8n, Ollama, Stirling-PDF, pdf-cleaner, LM Studio
  Hermes Agent (reconfigurado a local)
  betterbird, evolution, perfumes
  docker-admin, n8n-admin, ai-router

Única dependencia externa real: Hermes Agent necesita un provider de IA.
Si se reconfigura a Ollama o LM Studio, el laboratorio es 100% autónomo.

NIVEL 7 — TOMA DE DECISIONES
================================================================================

35 — ¿Aceptarías Kubernetes?

No.

Razones:
1. Sobredimensionado. El laboratorio tiene 4 contenedores. Kubernetes está
   diseñado para docenas o cientos.
2. Complejidad operativa. Añadir Kubernetes multiplica la superficie de
   aprendizaje y mantenimiento.
3. No aporta valor. No hay necesidad de escalado horizontal ni orquestación
   multi-nodo.
4. Contradice la filosofía operativa. No reduce trabajo futuro, no aumenta el
   conocimiento significativamente.

Decisión: mantener Docker Compose.


36 — ¿Aceptarías una base de datos externa para la documentación?

No.

Razones:
1. Markdown en Git es más mantenible. No necesita servidor ni backup específico.
2. Portabilidad. Los archivos .md se leen desde cualquier sitio.
3. Hermes los lee directamente sin necesidad de APIs.
4. Riesgo de vendor lock-in.

Decisión: mantener documentación en archivos .md dentro del repositorio.


37 — ¿Aceptarías sustituir Markdown por Notion?

No.

Razones:
1. Dependencia externa. Notion requiere internet.
2. Hermes no puede leer Notion directamente.
3. Sin versionado nativo (no es Git).
4. No mejora nada. Markdown ya es legible, editable y versionable.

Decisión: mantener Markdown como formato único de documentación.


38 — Tecnologías que rechazaría incorporar actualmente

Kubernetes — Sobredimensionado para 4 contenedores.
Base de datos externa para docs — Añade dependencia sin valor.
Notion para documentación — Rompe la autonomía local del agente.
CI/CD complejo (Jenkins, GitLab CI) — Un hook de Git basta.
Terraform/Pulumi — IAC para 4 contenedores es sobredimensionado.
Monitorización externa (Datadog, Grafana Cloud) — nvidia-smi + docker ps bastan.
Base de datos externa para n8n — SQLite basta para el volumen actual.

Criterio: cualquier tecnología que añada más complejidad operativa de la que
resuelve, se rechaza.


39 — Decisiones que NO tomaría en este momento

Migrar a Podman — Docker funciona, no hay problema que resolver.
Reemplazar DeepSeek como provider principal — Funciona. No cambiar sin motivo.
Añadir más servicios Docker — No hay necesidad. Los 4 actuales cubren todo.
Crear nuevas skills — Las 9 actuales cubren todo el dominio.
Automatizar healthchecks con herramienta externa — Cron + scripts funcionan.
Separar n8n en varios contenedores — Un contenedor basta.

Principio: no arreglar lo que no está roto. No añadir complejidad antes de que
exista la necesidad.
