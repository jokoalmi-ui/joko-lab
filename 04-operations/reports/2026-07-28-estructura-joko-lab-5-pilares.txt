═══════════════════════════════════════════════════════════
CONTEXTO
═══════════════════════════════════════════════════════════

El incidente del perfil Linux (desaparicion de ~/.local/share/uv)
ha cambiado el enfoque del proyecto. Ya no se trata solo de tener
un agente potente (Hermes), sino de construir un laboratorio
reproducible para estudiar, comparar y mejorar agentes de IA.

Joko Lab esta evolucionando de "un agente" a un sistema
operativo para trabajar con IA. No se trata de Prompt Engineering
sino de AI Engineering, donde el prompt es solo una pieza.

El laboratorio debe aprender de si mismo y hacer reproducibles
sus propias mejoras. Para eso se organiza en 5 pilares:
  1. Knowledge     → lo que sabemos (modelos, experimentos, datos)
  2. Infrastructure → lo que sostiene el lab (docker, recovery, inicio/fin)
  3. Automation   → lo que se ejecuta solo (scripts, cron, tests)
  4. Operations   → lo que registramos (informes, metricas, incidencias)
  5. Inference    → lo que hacemos con lo que sabemos (router, compiler)

El Prompt Compiler ya no es el nucleo del sistema. Es un
componente de 05-inference/compiler/. El sistema completo es
un Inference Engine que decide que modelo usar, que estrategia
aplicar, como validar y como retroalimentar el conocimiento.

Hermes deja de ser el centro del laboratorio. Pasa a ser uno
de varios backends de ejecucion (junto con Ollama, LM Studio,
Claude, Gemini, GPT, DeepSeek).

═══════════════════════════════════════════════════════════
CONCEPTOS CLAVE (incorporados en v3)
═══════════════════════════════════════════════════════════

AI Engineering > Prompt Engineering
  El prompt es una pieza, no el producto. El producto es la
  estrategia completa: que modelo, que parametros, que
  herramientas, que verificacion. El compilador genera el
  prompt como subproducto de esa decision.

Prompt Project
  No se guarda el prompt final. Se guarda la especificacion:
  objetivo, restricciones, contexto, destino, modelo, proveedor,
  temperatura, tool-use, formato esperado. Luego se "compila"
  para cada arquitectura destino obteniendo prompts diferentes
  para Gemini, Claude, DeepSeek o Gemma local a partir de la
  misma especificacion.

Ingenieria del Conocimiento
  Flujo vertical: idea → experimento → resultado → validacion
  → skill → automatizacion → monitorizacion → mantenimiento
  → evolucion. Cada paso deja evidencia reproducible.

Registro Continuo
  No puede depender de la memoria. Cada cambio entre sesiones
  debe quedar registrado. El protocolo inicio/fin con diff
  es la garantia de que el laboratorio no pierde contexto.

═══════════════════════════════════════════════════════════
PROMPT PROJECT (detalle)
═══════════════════════════════════════════════════════════

En lugar de guardar solo el prompt final, se guarda la
especificacion completa (Prompt Project). Luego se compila
para cada arquitectura destino.

Estructura de un Prompt Project:

  spec.yaml:
    project:
      id: PP-20260728-001
      name: "ejemplo-spa"
      version: 1.0.0

    objective:
      description: "Crear una SPA para gestion de aparcamientos"
      target_format: "Un unico HTML con Tailwind"
      constraints:
        - "Sin dependencias externas"
        - "Responsive"
        - "Comentarios en espanol"

    target:
      models:
        - gemini-2.5-pro
        - claude-sonnet-4
        - deepseek-v4
        - gemma-4-12b-local

    parameters:
      temperature: 0.2
      max_tokens: 4096
      tool_use: false

    experiment_tracking:
      - EXP-20260728-002

  compiled/                         # Generado al pulsar "Compile"
    prompt-gemini.md                #   Optimizado para Gemini
    prompt-claude.md                #   Optimizado para Claude
    prompt-deepseek.md              #   Optimizado para DeepSeek
    prompt-local-gemma.md           #   Optimizado para Gemma local

  experiments/                      # Resultados de cada ejecucion
    gemini-2.5-pro/                 #   Resultados con Gemini
    claude-sonnet-4/                #   Resultados con Claude
    deepseek-v4/                    #   Resultados con DeepSeek

═══════════════════════════════════════════════════════════
PROTOCOLO DE SESION (inicio / fin)
═══════════════════════════════════════════════════════════

No son scripts. Son un protocolo con dos implementaciones.

inicio:
  checks                → Verificar componentes (docker, ollama, uv, etc.)
  snapshot              → Generar estado-inicial.json
  diff                  → Comparar contra ultimo estado-final.json
  report                → Mostrar anomalias detectadas
  ready                 → Senal de laboratorio listo

trabajo:
  eventos               → Registrar eventos importantes durante la sesion
  checkpoint            → Guardar estado intermedio (si aplica)

fin:
  checkpoint            → Estado actual de todo
  snapshot              → Generar estado-final.json
  diff                  → Comparar con estado-inicial.json
  backup                → Git bundle + rescue (si hay cambios)
  log                   → Escribir informe de cierre
  close                 → Cerrar Hermes

El protocolo garantiza que cualquier anomalia (como la
desaparicion de ~/.local/share/uv) se detecta en el siguiente
inicio antes de empezar a trabajar.

═══════════════════════════════════════════════════════════
IDENTIDAD DE EXPERIMENTOS
═══════════════════════════════════════════════════════════

Cada experimento tiene un ID unico:

  EXP-YYYYMMDD-NNN

Ejemplo:
  EXP-20260726-001   Comparativa de 7 modelos (35 tests)
  EXP-20260728-001   Validacion de prompt-engineering skill

Cada experimento es un directorio con:
  README.md          Objetivo, condiciones, conclusiones
  config.yaml        Parametros exactos (modelo, seed, quant, temperatura)
  results.csv        Datos crudos

Esto permite consultas del tipo:
  "todos los experimentos con Gemma sobre JSON con temperatura 0.2"

═══════════════════════════════════════════════════════════
REGLAS DE LA ESTRUCTURA
═══════════════════════════════════════════════════════════

1. ~/joko-lab/ es la raiz unica. Todo el conocimiento del
   laboratorio vive aqui.

2. ~/hermes-lab/ sigue siendo el repo de Hermes. No se toca.
   Solo se referencian o enlazan componentes que pertenecen
   al laboratorio.

3. Los numeros (01-, 02-) no son prioridad, son orden logico.
   Knowledge va primero porque los otros pilares dependen de el.

4. Cada ficha de modelo es un archivo .md autocontenido con
   frontmatter YAML para que sea parseable por maquina.

5. inicio/ y fin/ son protocolos, no scripts sueltos. El script
   es solo una implementacion del protocolo.

6. Los experimentos tienen ID unico (EXP-YYYYMMDD-NNN) y son
   directorios autocontenidos con README + config + resultados.

7. Los datos originales (raw) se separan del conocimiento
   procesado. 01-knowledge/data/raw/ no se toca; los analisis
   van en 01-knowledge/experiments/ o 01-knowledge/benchmarks/.

8. Los informes van a 04-operations/reports/ fechados. No mas
   ~/informes-joko-lab/ suelto.

9. No se guarda el prompt final. Se guarda la especificacion
   (Prompt Project). El prompt compilado es un derivado.

10. No se confia en la memoria. Cada cambio entre sesiones
    queda registrado. El protocolo inicio/fin es obligatorio.

═══════════════════════════════════════════════════════════
NOTAS ARQUITECTONICAS
═══════════════════════════════════════════════════════════

- Hermes no es el centro de Joko Lab. Hermes es uno de varios
  backends de ejecucion. El valor diferencial esta en el
  conocimiento acumulado y en Inference Engine.

- El Prompt Compiler ahora es 05-inference/compiler/. Ya no es
  el nucleo del sistema. El nucleo es el Inference Engine
  completo (router → compiler → validators → executors →
  evaluators → feedback).

- 05-inference/feedback/ es el mecanismo que cierra el ciclo.
  Sin feedback, el laboratorio no aprende. Los evaluadores
  producen observaciones (E1), que pasan a hipotesis (E2) y
  se validan como conocimiento (E3) en Knowledge.

- Los protocolos inicio/fin no son especificos de Hermes.
  Cualquier agente que use Joko Lab debe implementarlos.
  Eso permite que el laboratorio sea independiente del backend.

- Las skills de Hermes dejan de ser simples colecciones de
  prompts. Pasan a ser conocimiento operativo, versionado y
  verificable, alimentado por el ciclo de ingenieria del
  conocimiento.
